# How the numbers are calculated

This document explains, in plain language, every calculation in the project: where each piece of data comes
from, where it is stored, how long it is kept, when it is used, and the formulas applied to it. File names
point to the code (all under `src/energy_advisor/`).

## 1. Where data lives

| Data | Comes from | Stored in | Kept for | Used by |
|---|---|---|---|---|
| Market (spot) prices | Energy-Charts or aWATTar APIs | `data/price_cache.sqlite`, table `spot_price` | **Forever** (published prices never change). Delete the file to refetch. | Price tool, scheduler, history generator, price estimate |
| Household history (consumption per device, PV production) | Generated by `seed-db` from past weather and past prices | `data/energy_data.db`, tables `energy_usage` and `solar_generation` | Until the next `seed-db`, which drops and recreates the tables | History tools, charts |
| Knowledge-base chunks and their embeddings | `knowledge_base/*.txt` + OpenAI embeddings | `data/vectorstore/` (Chroma) | Until `build-index --rebuild` | Knowledge-base search |
| Weather (forecast and past hours) | Open-Meteo API | **Not stored.** Fetched again on every request | – | Weather tool, PV forecast, scheduler, history generator |
| Place coordinates for other cities | Open-Meteo geocoding | In memory (per running process) | Until the program ends | Weather for places other than Munich |
| BM25 keyword index | Built from the stored chunks | In memory | Until the program ends | Knowledge-base search |
| Evaluation reports, charts | `eval`, `report` commands | `reports/` (or the folder you pass) | Until you delete them | You |
| Conversations (all messages of a chat, including tool calls and results) | The agent | In memory (LangGraph `InMemorySaver`), one thread per conversation | Until the program ends (CLI `chat`) or the Streamlit server stops; "New conversation" starts a new thread | Every following turn of the same conversation |

Nothing about **planned** device runs is stored anywhere. Each scheduling request is calculated on its own
(see [5.6](#56-why-a-second-device-does-not-know-about-the-first)).

## 2. Electricity prices

### 2.1 Fetching

When prices are needed for a time interval, the price service (`services/prices.py`) asks a chain of sources
and takes the **first one that covers at least 99 % of the interval**:

1. **Energy-Charts** (Fraunhofer ISE): day-ahead prices for Germany/Luxembourg in 15-minute steps, in EUR/MWh.
2. **aWATTar**: the same market, hourly steps. Used when Energy-Charts fails or rate-limits (HTTP 429).
3. **Estimate** for periods with no published prices yet (see 2.5).
4. **Synthetic profile**, a typical German price day, only if everything else fails (see 2.6).

Sources 1 and 2 go through the **cache** first (`clients/prices/cache.py`). If the cache already holds at least
99 % of the requested slots, they are returned without any API call. Otherwise the API is called, and every
slot it returns is written to `data/price_cache.sqlite`. Day-ahead prices for tomorrow are published around
13:00. Before that time, the APIs have no data for tomorrow, so the estimate is used.

A request spanning several days (for example today 15:00 to Thursday 07:00) is first sent as one request to
the real sources. If that fails because the later days are not published yet, each day is resolved
separately. Today keeps real prices and only the missing days are estimated. The answer then lists both
sources and is marked `is_estimate: true`.

### 2.2 From market price to household price

The market price is per MWh and excludes all fees. The household pays (`services/tariff.py`):

```
household price (EUR/kWh) = (market price / 1000 + surcharges) × (1 + VAT)
```

with surcharges = 0.19 EUR/kWh (grid fees, levies, electricity tax, concession fee, supplier margin) and
VAT = 19 %. Example: a market price of 100 EUR/MWh gives (0.10 + 0.19) × 1.19 = **0.345 EUR/kWh**. A negative
market price lowers the household price but rarely makes it negative, because the surcharges are added.

### 2.3 From 15-minute slots to hours

The scheduler works with the original 15-minute slots. For the price tool shown to the LLM, the four
quarter-hours of each hour are averaged (simple mean) to keep the answer short: 24 rows instead of 96.

### 2.4 Labels and summary of a day

For one local day, the price tool sorts the hours by price and labels:
- the cheapest third `off_peak`,
- the middle third `mid_peak`,
- the most expensive third `peak`.

It also reports the average, minimum and maximum price, the 4 cheapest and the 4 most expensive hours, and the
hours with a negative market price. The labels are relative to that day, not fixed price levels.

### 2.5 Estimate for unpublished days

(`clients/prices/estimate.py`) For each hour of the target day, the estimate takes the market price of the
**same local hour** on each of the **previous 7 days** (from the real sources, usually from the cache) and
averages them. Days with the same weekday as the target day count **twice**. Example: for a Sunday at 03:00,
with 50 EUR/MWh last Sunday and 100 EUR/MWh on the other six days: (2 × 50 + 6 × 100) / 8 = **87.5 EUR/MWh**.
This is an average of recent days, not a forecast: it ignores tomorrow's weather and public holidays.

### 2.6 Synthetic price profile

(`clients/prices/synthetic.py`) A fixed table of typical prices for each hour of the day (moderate at night,
high in the morning, low at midday, highest in the evening). Midday is made cheaper in summer and slightly
dearer in winter, each day gets a random level of ±20 %, and each hour gets ±6 EUR/MWh of noise. The random
numbers come from the date, so the same day always gives the same prices.

## 3. Weather

### 3.1 Fetching

(`clients/open_meteo.py`, `services/weather.py`) Weather is fetched from Open-Meteo **on every request** and
is not stored. One endpoint serves the past (about 3 months) and the future (up to 16 days). For Munich the
fixed coordinates from the settings are used; any other place name is first converted to coordinates
(geocoding), and that result is kept in memory while the program runs.

Requests are made in **UTC**, because local clock times are ambiguous on the night the clocks go back
(02:00-03:00 happens twice). Our code converts to local time afterwards.

A live answer is accepted only if it covers at least **90 %** of the requested hours. Otherwise the synthetic
weather (3.4) is used and the answer says so.

### 3.2 Solar radiation alignment

Open-Meteo reports radiation as the **average over the previous hour**: the value labelled 13:00 belongs to
12:00-13:00. The code shifts it so that each hour row holds the radiation measured during that hour.

### 3.3 Sky condition and daily summary

Open-Meteo weather codes are mapped to four conditions: 0-1 `sunny`, 2 `partly_cloudy`, 3 and fog `cloudy`,
everything else (rain, drizzle, snow, showers, thunderstorms) `rainy`. A day's condition is the most frequent
condition between 08:00 and 17:00. The forecast tool also reports each day's lowest and highest temperature and
its highest irradiance.

### 3.4 Synthetic weather

(`domain/climate.py`, `domain/solar.py`) Used when the API is unavailable:
- **Sun height** for every hour is calculated from the date, the time and the coordinates (standard
  astronomical formulas). This gives the correct sunrise, sunset and midday sun height for Munich in every
  season.
- **Clear-sky radiation** = 1098 × sin(sun height) × e^(−0.057 / sin(sun height)) W/m² (Haurwitz model),
  averaged over three moments within the hour.
- Each day gets a random sky condition (more cloud from October to March). The radiation is multiplied by 1.0
  (sunny), 0.6 (partly cloudy), 0.3 (cloudy) or 0.12 (rainy).
- **Temperature** = Munich's average for that month ± 3 °C per day, plus a daily swing of ±4.5 °C that peaks
  around 15:00.

The random numbers come from the location and the start date, so the same request gives the same weather.

## 4. Solar yield and solar surplus

### 4.1 PV yield

(`domain/solar.py: pv_energy_kwh`)

```
PV energy in one hour (kWh) = installed power (kWp) × radiation (W/m²) / 1000 × performance ratio
```

with 8 kWp and a performance ratio of 0.8 (the share left after inverter, temperature and other losses).
Example: 500 W/m² for one hour gives 8 × 0.5 × 0.8 = **3.2 kWh**. The radiation is the value on a
**horizontal** surface; the tilt and direction of the real panels are ignored.

### 4.2 Solar surplus

(`optimization/service.py: solar_surplus`) The part of the PV energy that a flexible device could use:

```
surplus in one hour = max(0, PV energy − household base load in that hour)
```

The base load is 0.3 kW on average, shaped by a typical day profile: lower at night, higher in the morning and
evening (`domain/household.py`). Other devices that might run at the same time are not subtracted.

### 4.3 PV forecast tool

`estimate_pv_generation` calculates 4.1 and 4.2 for every hour of the next 1-3 days from the weather forecast
and returns per day: total PV energy, total surplus, and the 4 hours with the largest surplus.

## 5. Scheduling: the cheapest window

(`optimization/service.py`, `optimization/scheduling.py`)

### 5.1 The window

- **Start:** the start time given by the user (or set in the app); by default **now**. It is rounded up to
  the next quarter hour, and a start in the past becomes now.
- **End:** the deadline given by the user (or set in the app). If none is given: **24 hours after the start**,
  and the result says so, so the agent can ask by when the device is needed. The user can answer in the same
  conversation and the agent recomputes with that deadline (the conversation is remembered, see section 1).
- At most 7 days long. A deadline before the start is an error.

### 5.2 The input slots

1. Prices for the window come from the price service (section 2): 15-minute slots where published, hourly
   where estimated.
2. Each slot gets the household price (2.2) and the solar surplus of its hour (4.2) from the current weather
   forecast.
3. The first and last slot are cut to the window if needed.

### 5.3 Cost of energy in one slot

Using your own solar power is not free: you lose the payment you would have received for exporting it. So
solar energy is valued at the **feed-in tariff** (0.078 EUR/kWh), its *opportunity cost*.

In a slot, energy is taken from the cheaper source first:
- normally solar first, up to the surplus available in that slot, at 0.078 EUR/kWh, and the rest from the grid
  at the slot's household price;
- if the household price is **below** the feed-in tariff (only with very negative market prices), everything
  comes from the grid and the solar power is exported.

### 5.4 Two kinds of devices

**Devices that may pause (EV charging, `interruptible=true`).** Every slot offers two portions: the solar
portion (as much as the surplus allows, at 0.078 EUR/kWh) and the grid portion (the rest of the device power,
at the household price). All portions of all slots are sorted from cheapest to most expensive, and they are
filled in that order until the requested energy is reached. Taking the cheapest energy first always gives the
lowest total cost, because each kWh's cost does not depend on the others. A slot that is only partly used
means charging at a lower average power during that whole slot, as a wallbox following the solar surplus does.
Neighbouring used slots are joined into one block.

**Devices that must run without pause (dishwasher, washing machine, `interruptible=false`).** The device runs
at constant power for `energy / power` hours (e.g. 1 kWh at 0.5 kW = 2 hours). For **every possible start
time** (each slot start in the window), the code adds up the cost over the slots the run would cover (partial
slots count proportionally) and keeps the cheapest start. If two starts cost the same, the earlier one wins.
Starts whose run would end after the deadline are not allowed.

### 5.5 Baseline and saving

The **baseline** is the cost of starting immediately at the start of the window and running at full
power without pause. **Saving = baseline cost − cost of the recommended schedule.**

Example (interruptible, 6 kWh, 11 kW, three hours priced 0.30, 0.30, 0.20 EUR/kWh, 4 kWh of surplus in the
second hour): 4 kWh of solar at 0.078 + 2 kWh in the 0.20 hour = **0.71 EUR**. The baseline runs in the first
hour at 0.30: 6 × 0.30 = 1.80 EUR. Saving: **1.09 EUR**.

### 5.6 Why a second device does not know about the first

Each call of `find_cheapest_window` is calculated **from scratch** and nothing is saved afterwards:
- prices are cached, but prices are the same for everyone, so sharing them is correct;
- the solar surplus is recalculated from the weather forecast on every call, always as the full surplus;
- the schedule of the first device is returned to the LLM but is **not recorded** as "this surplus is taken".

So if you ask the **chat** about the EV and then about the dishwasher for the same hours, both plans count the
same solar energy, and the total cost of both is too low.

The app's **Planner** avoids this: it schedules all chosen devices in one go (`plan_devices`). Devices are planned
one after another, the largest energy first. After each device, the solar energy it takes in each slot is
subtracted, and the next device only sees what is left. The table therefore never shows the same solar kWh
twice.

## 6. The household's history

(`data/seed.py`, command `seed-db`) The history is synthetic, but driven by the **real weather** of the past
days in Munich (3.1) and the **real household prices** of each past hour (2.1, 2.2). For every hour:

| Device | Calculation |
|---|---|
| **Base load** (fridge, router, lighting, cooking...) | 0.3 kW × day-profile factor of that hour × random 0.85-1.15 |
| **Heat pump** | Heat needed = 0.15 kWh per °C that the outdoor temperature is below 15 °C, plus hot water (0.8, 0.6, 0.6, 0.5 kWh at 06, 07, 19 and 20 h). Electricity = heat / COP, where COP = 3.0 + 0.1 × outdoor °C, limited to 2.0-4.5. Example at 0 °C: heat 2.25 kWh, COP 3.0, electricity **0.75 kWh**. |
| **EV** | Each day the car drives 35 km × random 0.5-1.5 at 17 kWh/100 km, which adds to the "missing" energy. When at least 15 kWh are missing, the car charges (85 % chance that day) from 17, 18 or 19 h at 11 kWh per hour until full or midnight; any rest carries over to the next day. |
| **Dishwasher** | 75 % chance per day, starts at 19, 20 or 21 h, 0.6 + 0.4 kWh over two hours |
| **Washing machine** | 50 % chance per day, starts between 08 and 18 h, 0.5 + 0.3 kWh |
| **Dryer** | after 60 % of washes, 2 hours later, 0.6 + 0.6 kWh |
| **PV** | Formula 4.1 with the real radiation of that hour; stored only for hours with radiation |

Appliance energies vary randomly by ±10 %. Each consumption row stores its **cost = kWh × household price of
that hour**, before any solar is subtracted. The random generator starts from a fixed seed (default 42), so
the same inputs always give the same history. At most 90 days, ending yesterday.

## 7. Summaries of the history

(`data/aggregation.py`) All days and hours are **local** (Munich) time.

### 7.1 Consumption (`query_energy_usage`)

For the requested days, optionally one device type:
- totals: kWh and EUR, per device type, per device and per day;
- average kWh per day = total kWh / number of days in the range;
- average price paid = total EUR / total kWh;
- average kWh in each hour of the day = all kWh in that hour / number of days;
- the raw hourly rows only if there are at most 40 (otherwise the LLM's context would overflow).

### 7.2 Solar production and energy balance (`query_solar_generation`)

Production per day (with the day's most frequent sky condition), per sky condition and per hour of day, and
average per day. Then, **hour by hour**, consumption is matched with production:

```
used at home   = min(consumption, production)
exported       = production − used at home
from the grid  = consumption − used at home
```

Summed over the period:
- **self-consumption rate** = used at home / production (how much of your solar you used);
- **autarky** = used at home / consumption (how much of your need solar covered);
- grid cost = grid energy × that hour's price;
- saved by self-consumption = solar used at home × that hour's price;
- feed-in revenue = exported × 0.078 EUR/kWh.

### 7.3 Recent summary (`get_recent_energy_summary`)

Consumption per device type and total production over the last N hours (default 24), counted back from **now**.
Because the generated history ends yesterday at 23:59, "the last 24 hours" only contains the hours from
yesterday that fall within those 24 hours. Asked at 18:00, that is only 18:00-24:00 of yesterday, so the
numbers look very small.

## 8. Savings and CO₂

(`services/savings.py`, tool `calculate_energy_savings`)

```
current cost    = current kWh × current price
new cost        = new kWh × new price         (new price = current price unless given)
saving          = current cost − new cost
saving %        = saving / current cost
saving per year = saving × 365
CO₂ saved       = (current kWh − new kWh) × 0.36 kg/kWh
```

Two uses:
- **Use less:** new kWh smaller, same price. Saves money and CO₂.
- **Shift in time:** same kWh, cheaper price (or the feed-in tariff for solar hours). Saves money but **no
  CO₂** in this model, because the same energy is still used.

The yearly figure assumes the same saving every day. Without a price, the tool uses a typical fixed tariff of
0.35 EUR/kWh.

The savings chart (`report` command) uses the same formula with the prices of **one day (tomorrow)**, the
average daily heat-pump use of the last 30 days, and the exported solar energy of the last 30 days, each
multiplied by 365.

## 9. Knowledge-base search

(`rag/`, tool `search_energy_tips`)

### 9.1 Building the index (once)

Each document is cut into pieces of up to 1,000 characters, overlapping by 200 characters so that no sentence
is lost at a boundary. Each piece is turned into a list of numbers (an *embedding*, OpenAI
`text-embedding-3-small`) that represents its meaning, and stored in Chroma (`data/vectorstore/`).

### 9.2 Answering a query

1. **Vector search:** the question is embedded as well, and the 10 pieces with the closest meaning are found.
2. **Keyword search (BM25):** the 10 pieces that share the most (and the rarest) words with the question.
   Pieces without any shared word are ignored.
3. **Fusion (Reciprocal Rank Fusion):** each piece gets `1 / (60 + its rank)` from each list it appears in,
   and these are added up. Example: rank 2 in both lists gives 1/62 + 1/62 = 0.032, more than rank 1 in only one
   list (1/61 = 0.016). The top 8 (or more if more results are requested) go on.
4. **Re-ranking:** a language model reads the question and the first 700 characters of each candidate and
   gives each a score from 0 to 10. Candidates below 3 are dropped (at least one is always kept). Candidates the
   model forgot to score are placed after the scored ones.
5. Each tip is labelled `high` (score ≥ 7), `medium` (≥ 4) or `low`. If re-ranking fails, the fused order is
   used and the first two tips are labelled `high`, the next two `medium`.

### 9.3 Benchmark (`rag-benchmark`)

For 12 questions with a known correct document:
- **hit@3** = share of questions where the correct document is in the top 3;
- **MRR** = average of 1 / (rank of the correct document), counting 0 when it is missing.

## 10. Evaluation scores

(`evaluation/`)

For each test case:
- The **judge** (a language model) gives accuracy, relevance, completeness and usefulness from 0 to 1, using
  the tool outputs as the truth. **Response overall** = the average of the four.
- **Tool appropriateness** = expected tools that were used / all different tools used. Extra tools lower it.
- **Tool completeness** = expected tools that were used / all expected tools.

For the whole run:
- each metric is averaged over the cases;
- **response score** = average response overall;
- **tool score** = (average appropriateness + average completeness) / 2;
- **overall score** = (response score + tool score) / 2;
- cases with response overall below 0.7 or missing expected tools are listed as "need attention".

## 11. Time and dates

(`timeutils.py`)
- "Today", day boundaries and hour-of-day are always **Munich local time**. Calculations and storage use
  **UTC**.
- A local day is converted to a UTC interval from local midnight to the next local midnight. Such a day has
  24 hours, but **23** on the last Sunday of March and **25** on the last Sunday of October. Steps through a
  day are always taken in UTC, so these days are handled correctly.
- Dates given to tools must be `YYYY-MM-DD`; times `YYYY-MM-DDTHH:MM` (local).
- The agent receives the current local date and time and a calendar of the next 8 days, with today and
  tomorrow marked, to turn "tomorrow" or "Wednesday" into exact dates.
